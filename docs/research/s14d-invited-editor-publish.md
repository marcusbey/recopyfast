# Research — Story s14d-invited-editor-publish

## Verdict first

The story premise is confirmed in production and source. A device grant with
`view`, `edit`, and `publish` can authenticate, enter edit mode, and persist a draft, but the
invited-editor banner offers no Publish control. The backend Publish route already accepts the
grant and grades `publish`; the missing user action is the broken boundary.

`docs/reviews/stories.md` currently ends `Stories ready: no`. That review predates this live bug
story and concerns the original backlog's dependency/numbering defects. The user explicitly
authorized this bounded repair on 2026-09-19, including its plan-validation checkpoint.

## Current flow and anchor points

1. Owner enrolment: `SiteEditorsCard` → `POST /api/editor/editors` writes `site_editors`.
2. Editor authentication: `/edit` → request/submit code → hub session → handoff create/redeem.
3. Widget identity: `initEditorAuth()` → `applyEditorIdentity()` enables `editMode`.
4. Draft write: `persistContentUpdate()` sends `X-RCF-Editor-Grant` to
   `PUT /api/staging/content/:siteId`.
5. Publish backend: `showPublishConfirmation()` already sends the same header to
   `POST /api/staging/publish`; `validateEditorTokenFromRequest` and
   `requireEditorPermission(access, "publish")` grade it server-side.
6. Broken UI boundary: `showEditorBanner()` renders mark, editing claim, email, save status and
   Done only. Its tombstone says Publish would answer 401, but that statement became false when
   s14a opened the publish route to device grants.

## Permission and security invariants

- Only `publish` or `admin` renders Publish. `edit` permits draft writes only; `view` remains inert.
- The grant remains header-only. No query, fragment, body field, local report or log may carry it.
- Server-side permission checks remain authoritative. UI hiding is not authorization.
- Origin/site/device pinning and fresh parent-row revocation checks remain unchanged.
- `/api/edit-board/*` remains out of reach for a device grant.
- Publish confirmation still counts pending changes and requires an explicit second action.

## Terminal-session failure

The shared Save catch still calls `alert(...)` for every error and returns while the editable DOM
and Save button remain active. `persistContentUpdate()` discards the HTTP status when it throws,
so callers cannot distinguish a terminal 401/403 from a transient 500/network error.

Minimum repair:

- retain response status on the thrown Error;
- on 401/403, store the typed content in `sessionStorage` under site + element, leave it visible,
  remove contenteditable, disable mutation controls, and set one inline banner status;
- open re-authentication in a new tab so the draft page remains intact: editor hub for a device
  grant, owner dashboard/sites for an edit-session token;
- keep non-auth errors on the existing retryable path.

is the final evidence, not a substitute for these tests.

## Implementation discoveries

- Publish's preview GET was not using the same credential helpers as its POST. A device grant
  therefore reached the confirmation without authenticating the pending-change count. The
  implementation reuses `editorTokenQuery()` and `editorAuthHeaders()` for that GET.
- The invited-editor banner lacked the existing `data-rcf-ignore` marker. Its own Publish/Done
  controls acquired content IDs and clicks could start editing those controls. The lead approved
  the one-attribute repair inside this story because it is required for the touched controls to
  work. A real-source regression asserts neither discovered content IDs nor contenteditable
  appears inside the banner.
- CSS comment prose inside a template string survives JavaScript minification. Moving those
  explanations to adjacent JavaScript comments frees bytes without changing styling or removing
  features; no gzip ceiling change is necessary.

## Bundle constraint

Baseline on the deployed revision:

```text
bundle 46,540 B gzip (ceiling 46,681)
widget 33,750 B gzip (ceiling 33,865)
```

The widget has only 141/115 bytes of headroom. Do not raise either ceiling. Prefer reuse and
deletion: the new Publish button calls the existing confirmation method and uses existing strings;
remove obsolete invited-editor commentary/runtime text or another provably dead byte source if the
behavioural change exceeds the ratchet.

## Complexity

2, matching the story. The authorization and persistence mechanisms already exist; the work is a
small UI parity correction plus terminal-state hardening in the same edit lifecycle.

## Open questions

None that changes implementation. The user's explicit acceptance settles that invited editors with
publish permission must perform an explicit Publish, rather than auto-publish on Save.
