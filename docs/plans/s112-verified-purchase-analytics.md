# Plan — s112-verified-purchase-analytics

Date: 2026-10-12. Depends on released s107, s110, s111 and current s82 billing reconciliation. Branch: `feature/s112-verified-purchase-analytics`. Research: [s112](../research/s112-verified-purchase-analytics.md). Independent review passed; human validation received2026-10-12.

## Result and financial definitions

Verified live payments produce one GA `purchase` per canonical transaction when valid consent/context exists. First-party aggregate counts distinguish all verified live paying accounts, new paying accounts, transactions, renewals, refunds/net money and current paid entitlement. The GA subset is labelled as such. Unknown legacy mode is unknown, never assumed live. No new financial ledger duplicates existing billing tables/events.

The first positive live payment for a recognized product makes an account a historically paying account; a renewal does not make another customer. Fully refunded/chargeback-lost accounts can remain historically paid while their net retained amount/current entitlement is zero. Automatic duplicate/lifetime-covered charges that are returned are excluded from successful-customer acquisition. Never describe trial Pro as paid.

## Canonicalization and reuse

Use existing processed `billing_events`, authoritative Stripe objects and `billing_invoices`, `plan_entitlements`, `credit_purchases` as evidence. The ledger stores `event.data`, not the full envelope: obtain event-level `livemode` through a bounded `stripe.events.retrieve(stored_event_id)` and cross-check the recognized payment/invoice object's mode. Never assume the JSON already contains envelope mode, infer mode from a Stripe ID prefix, or treat configured live credentials as proof. If an old event is unavailable, mode mismatches, or provider proof cannot be established, classify the candidate unknown/suppressed and expose that count; no live conversion is emitted. The s111 outbox is the only new delivery ledger. Unique source keys include mode and canonical transaction: subscription invoice identity versus one-off payment-intent identity. Resolve parentage so Checkout, payment intent and invoice cannot count one transaction twice. Store an opaque random transaction UUID once in the outbox and reuse it for GA purchase/refund; keep source IDs internal. Select context against the authoritative true payment occurrence, never reconciliation/dispatch time: require server capture at or before occurrence, effective-consent interval covering it and verified same-account binding. Among eligible contexts choose latest captured_at then stable context UUID order. Atomically freeze the choice or explicit absent disposition under the canonical source key. Later consent grants, campaigns, account devices or replacement context cannot fill absent attribution or replace revoked/expired choice. Context FK cleanup never triggers reselection. Dispatch claim independently rechecks current revocation/expiry of that frozen choice.

Reconciliation runs only on successfully processed known billing events using bounded indexed anti-join discovery against private analytics source receipts, with **no created-at cutoff or finite overlap**. All candidates also require a currently existing source account; deletion cannot be undone by reconciliation. A source that becomes processed days later remains discoverable. Add a partial index for processed relevant source types, plus a minimal `analytics_delivery_sources` receipt keyed uniquely by Stripe event ID, with normalization state, next-attempt time and optional outbox reference. This is pipeline bookkeeping, not copied payment/account truth. Enable RLS and revoke PUBLIC/anon/authenticated access in the same migration; service-only atomic functions and effective-grant tests match the outbox boundary. Persist pending source ownership before doing normalization; complete the receipt atomically with canonical enqueue or a final typed no-op/suppression. A crash/retryable normalization error keeps a due pending receipt; expired normalization claims can be reclaimed because no Google send occurs in this phase. Process new sources and due retries in bounded fair batches so a poison source cannot starve newer ones. Source normalization retries are distinct from uncertain Google delivery and never reset a `sending`/`uncertain` outbox row. A reconciliation failure is observable and retryable before sending; it never changes financial handlers. Refund handling reads current authoritative outcome before normalization so out-of-order duplicate-protection events are not published as customer wins. A payment later genuinely refunded retains purchase history and gains a distinct refund correction; partial refunds use their own unique refund IDs and actual amounts.

First-payer counts are derived from the minimum qualifying transaction time grouped by authoritative account, not another per-user ledger. Persist the resulting fixed `customer_type: new|returning` classification with an enqueued purchase, if exposed to GA, so a dispatch retry cannot reclassify it. Derive it from all verified qualifying payment evidence, not only the GA subset or webhook arrival order; unresolved predecessor evidence stays unclassified rather than guessed new. GA client IDs and GA user counts are not unique billing accounts. All-user aggregate reporting does not depend on whether a GA outbox row was suppressed. Legacy/test/unknown exclusion rules are explicit in the canonical query/runbook. Use bounded operator queries/readouts; no reporting UI is required.

## Implementation correctness clarification

These rules refine the approved payment-evidence adapter; they preserve seven tasks, human validation and the no-financial-mutation boundary. The matching research addendum pins current source/SDK fields.

- **Settlement:** freeze context against defensible successful-payment occurrence. Use original successful payment event time, invoice `status_transitions.paid_at`, or the relevant paid invoice-allocation timestamp as appropriate to that canonical transaction. Never use PI/Checkout creation, local invoice `created_at`, webhook receipt time, or `lifetimePaymentTime()` (which reads PI `created`) as settlement. If only Checkout completion is known and actual settlement cannot be established, keep it unknown rather than fabricate attribution time.
- **Collected cash:** inspect paid invoice allocations and underlying successful PI/charge. Invoice `amount_paid` can include customer credit. Allocate only the actual paid share to each invoice; never copy one PI's whole amount into multiple invoice purchases. Unsupported partial/mixed-credit/ambiguous allocation remains unknown and is reported. No refund/provisioning function is invoked from analytics.
- **Successful refunds:** normalize unique authoritative refund IDs and count returned money only for `status=succeeded`. Pending/requires-action is pending normalization; failed/canceled is not refunded revenue. Observe pending receipts again until a known terminal outcome. Identify automatic exclusions using exported `COVERED_BY_LIFETIME` (`covered_by_lifetime`) plus subscription metadata, or `duplicate_founding_lifetime` plus founding reservation. Do not reuse monetary helpers whose “live” refund includes pending states as the accounting success test.
- **Disputes:** creation is provisional; closed status and actual relationship to any refund govern the outcome. Keep dispute/refund source identities distinct and do not subtract the same principal twice. If overlap cannot be reconciled, expose unknown net amount rather than manufacture an exact total.
- **Currency:** current catalog checkout uses USD. The bounded adapter accepts verified USD and converts its minor units by 100; unsupported currency is explicitly suppressed/unknown. Prices/items still come from catalog and verified transaction data. No new currency dependency or universal cents assumption.
- **History:** when prior event/object proof is unavailable, verified payer counts are a lower bound, not a claim that every historical payer is known. An absent older row does not prove new-customer status. Persist/emit `customer_type` only when proof establishes new/returning; otherwise omit it and expose the history-incomplete count.

## Independent readiness-review clarification

An identified automatic refund in pending/requires-action state keeps the associated purchase
normalization pending; do not emit acquisition while its exclusion is unresolved. A succeeded
automatic return excludes that purchase. A failed/canceled return requires fresh payment
qualification and never counts as returned money. Test that purchase-versus-refund ordering.

One charge.refunded source can expose several refund IDs. Complete the authoritative pagination,
deduplicate each refund independently, and keep the source retryable while any child remains
unresolved. Its optional single outbox reference is not a one-source/one-refund assumption.
When one payment funds several invoices, allocate refunded principal to the canonical invoice
purchases using authoritative evidence; if allocation cannot be established, retain unknown
rather than applying the full refund to each invoice. Include these fixtures in T1/T3/T4.

The fresh review found these bounded clarifications sufficient; no additional feature or
human product decision is introduced. Existing settlement, cash, currency and history rules
remain as validated and clarified above.
