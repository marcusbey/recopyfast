# Plan — Story s18-stack-recipes

Branch: `feature/s18-stack-recipes`
Research: `docs/research/s18-stack-recipes.md` — read it first; this plan does not repeat it.
Design: `docs/designs/s18-stack-recipes.md` — marketing surface, reuses `HowItWorks.tsx`'s
code-panel + copy-button pattern. This plan does not repeat that spec either.
Depends on: `s17-cluster-engine` (engine — sitemap block convention, `src/lib/seo/json-ld.ts`),
`s02-install-verified` (owns `src/lib/sites/install-recipes.ts`, the recipe data this story
renders from). **Both must have landed before this plan executes** — this plan assumes their
shapes, it does not build them.

## Target story

**s18-stack-recipes — a verified install page for my stack.** Complexity 3.

Acceptance criteria:
- [ ] `/cms-for/<stack>` renders for at least wordpress, shopify, webflow, squarespace, framer,
  next-js, astro and plain-html.
- [ ] Each page renders from the install-recipe module `s02` owns — no second copy of the
  instructions exists.
- [ ] Each page names the exact file or admin location where the snippet goes for that stack.
- [ ] Each stack's snippet has been installed on a real instance of that stack and verified live,
  with evidence committed to the repository.
- [ ] Each page is reachable from the comparison cluster and appears in the sitemap.
- [ ] A stack where install is not actually possible is documented as unsupported rather than
  omitted silently.

## Install-instruction drift sites found (context, not this story's scope to fix)

1. **`src/components/sections/HowItWorks.tsx:26-38`** — the marketing landing page hardcodes a
   *static string copy* of the snippet shape, kept in sync only by a code comment
   (`:7-25`), not by import from `buildEmbedScript`. Already drifted once (per research). **This
   story does not touch it** — out of `s18`'s stated scope, recorded so a future story converges
   it rather than this one silently expanding scope.
2. **Dashboard `awaiting-install` state (`s02`, not this story)** — the second real consumer of
   install-location text, alongside this story.
3. **`/cms-for/<stack>` (this story)** — the third. Convergence rule this plan enforces: every
   snippet shown on `/cms-for/*` is `buildEmbedScript()`'s literal output (or a value already
   generated by it), never a third hand-typed copy — task 2's test asserts this mechanically.

`buildEmbedScript()` (`src/lib/sites/embed-script.ts:83-99`) remains the single generator of raw
snippet text; `s02`'s recipe module is expected to layer location/verification metadata around
that, not re-generate the tag itself.

## Tasks (ordered)

1. [ ] **Confirm the recipe module contract.** Import `InstallRecipe` (stack slug, display name,
   `location: string` — exact file/admin path, optional snippet-variant note, optional
   `unsupported: {reason: string}`), `getInstallRecipe(stack)`, `getAllInstallRecipes()` from
   `src/lib/sites/install-recipes.ts` (`s02`'s module, per its research's named candidate path). If
   the real shape differs from this plan's assumption, adapt this story's data-access layer to
   match `s02`'s actual shape before continuing — do not modify `s02`'s module to fit this plan.
   - Test: type-check imports cleanly; `getAllInstallRecipes()` returns entries covering all 8
     required stack slugs (wordpress, shopify, webflow, squarespace, framer, next-js, astro,
     plain-html).
2. [ ] **`/cms-for/[stack]/page.tsx` — supported variant.** Server component,
   `generateStaticParams` from `getAllInstallRecipes()`'s slugs, `notFound()` on unresolved slug.
   Render per the design doc: hero, dark code-panel snippet (reusing `HowItWorks.tsx`'s
   copy-button visual pattern) showing `buildEmbedScript()`'s output for a representative fixture
   site, exact-location card from `recipe.location`, "verified live" evidence card, footer CTA.
   - Test: rendering a known supported stack (e.g. `next-js`) asserts the displayed snippet text
     equals `buildEmbedScript({...fixture})`'s output byte-for-byte — the mechanical "no second
     copy" check.
3. [ ] **Documented-unsupported branch.** Same template, driven by `recipe.unsupported` — replaces
   snippet/location/evidence with an explanatory card (`Info` icon, sky tone, `unsupportedReason`
   text, "what to do instead" line). Never rendered with a `tone-danger`/red treatment.
   - Test: a fixture entry with `unsupported: {reason: "..."}` renders the reason text and does
     not render a snippet or copy button.
4. [ ] **`/cms-for` index.** Grid of every recipe from `getAllInstallRecipes()`, supported and
   unsupported both listed (never silently omitted).
   - Test: the index page lists all ≥8 seeded stack slugs as links, including any marked
     unsupported.
5. [ ] **Sitemap + cross-link.** Add a `/cms-for/<stack>` block to `src/app/sitemap.ts` (same
   per-cluster convention `s17` established); add a link to `/cms-for` from `/alternatives/*`'s
   migration-note or FAQ section — the "reachable from the comparison cluster" AC.
   - Test: sitemap output includes all ≥8 `/cms-for/<stack>` URLs; an `/alternatives/<slug>` page
     render asserts a link to `/cms-for` is present.
6. [ ] **Automated live-install verification — CI-spinnable stacks.** New
   `e2e/cms-for-verification.spec.ts`, extending `e2e/share-edit-publish.spec.ts`'s
   `startTargetServer()` pattern, for plain-html, next-js and astro (each gets a minimal real
   fixture app booted in the test), installing the real snippet from `getInstallRecipe()` and
   asserting via Playwright that the widget mounts with zero console errors and no uncaught
   exception (AGENTS.md non-negotiable #4). Attempt the same for wordpress via a Docker/wp-cli
   fixture; if that proves infeasible within CI's time budget, downgrade wordpress to task 7's
   manual track and record why in its evidence log.
   - Test: this task's deliverable is the spec file itself; a green CI run against it is the
     verification for however many of {plain-html, next-js, astro, wordpress} it covers.
7. [ ] **Manual verification — hosted-SaaS stacks.** For shopify, webflow, squarespace, framer
   (and wordpress, if task 6 downgrades it): perform a real install on a real trial/free account,
   capture a screenshot showing the widget/Edit Board mounted live, and commit evidence to
   `docs/verification/s18-stack-recipes/<stack>/` as: a dated markdown log (timestamp, tester,
   account/instance reference, exact steps, exact snippet used, outcome) plus at least one
   screenshot referenced from the log. An unsupported stack's log records the actual failed
   attempt and why, not an assumption.
   - Test: none automatable for content quality (human-judged at `/ks-review`); task 8 checks
     structural presence.
8. [ ] **Evidence-presence gate.** A small check (Jest test reading the filesystem, or a CI step)
   that fails if any `getAllInstallRecipes()` entry lacks either a
   `docs/verification/s18-stack-recipes/<slug>/` directory with ≥1 file, or an `unsupported`
   reason — closing the "mark unsupported to dodge verification" gap research flagged.
   - Test: a fixture recipe with neither evidence nor an `unsupported` reason fails the check; one
     with either passes.

## Run interdicts

- Do not modify `src/components/sections/HowItWorks.tsx` — the pre-existing, separately-owned
  drift site listed above is explicitly out of this story's scope; converging it is future work.
- Do not build `s02`'s dashboard `awaiting-install` UI — this story only consumes the data module.
- Do not fabricate verification evidence for any stack — an `unsupported` entry must show a real
  attempted-and-failed install, not a guess that it wouldn't work.
- Do not gate `/cms-for/*` against the embed byte budget (`s06`) — ordinary marketing pages, not
  the embed bundle.
- Do not hand-type a second copy of the snippet anywhere on `/cms-for/*` — every rendered snippet
  must trace to `buildEmbedScript()`'s output.
- If `s02`'s module doesn't exist yet when this plan is picked up for execution, stop — this is a
  blocked dependency, not something to work around with a local stub.

## The point everything turns on

Whether `src/lib/sites/install-recipes.ts` — once `s02` actually ships it — matches the
`InstallRecipe` contract task 1 assumes (`location: string`, optional `unsupported: {reason}`).
`s02`'s own research only names the path as a *candidate*, not a confirmed shape; task 1's
type-check-first approach exists precisely so a mismatch surfaces immediately as a build failure,
not as a runtime surprise three tasks later. Compare this plan's assumed shape against `s02`'s
actual plan/execution once available, before starting task 2.

Second: whether WordPress can genuinely be CI-automated (Docker + wp-cli, within CI's time
budget) or must join the four hosted-SaaS manual-evidence track. Task 6 discovers this in
practice; either outcome is acceptable, but silently skipping WordPress evidence entirely is not
— task 8's gate exists to make that impossible.

## Test strategy

Jest for: the recipe-module contract check, snippet-equals-`buildEmbedScript()`-output assertion,
supported/unsupported branch rendering, index page, sitemap merge, evidence-presence gate.
Playwright (`e2e/`) for the CI-spinnable stacks' live-install verification. Manual, human-produced
evidence (screenshot + dated log) for the hosted-SaaS stacks, checked for structural presence by
the Jest gate and for substance at `/ks-review`.

## Definition of Done

Repo DoD (lint, type-check, build, test green; single PR; review passed) plus:
- All ≥8 stacks render (supported or documented-unsupported, never omitted).
- Every rendered snippet traces to `buildEmbedScript()` — zero second copies.
- Every stack has committed evidence or a stated unsupported reason; the presence gate passes.
- `/cms-for/*` appears in the sitemap and is linked from `/alternatives/*`.
